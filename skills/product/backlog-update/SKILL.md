# プロダクトバックログの更新（backlog-update）

作品本応募（12/27）までのやることと進み具合は、[`app/planning/プロダクトバックログ.md`](../../../app/planning/プロダクトバックログ.md)（main）だけで管理する。

## 手順

1. `git pull` して最新にする（ほかのメンバーが自分の行を直していることがある）
2. 貼られたチャット・議事録・報告から、バックログに関わることだけを拾う（下の「拾い方」）
3. md を直す（下の「直し方」）。表の形は変えない
4. バーンダウンを描き直す：`cd app/planning/scripts` → `python burndown.py`（今日の日付で描く）
5. 「バーンダウン」の節の「最終更新」の日付を直し、末尾の「更新履歴」に1行足す
6. 何を変えたかを、表で短く報告する（直した行・足した行・状態を変えた行）。残り件数と理想との差も一言
7. コミット・プッシュは、頼まれたときだけ。頼まれたら main にコミットしてプッシュする

## 拾い方

| チャットの中身 | バックログでの扱い |
|---|---|
| 「〇〇できた」「確認できた」「表示できるようになった」 | その行を「完了」にし、完了日に発言の日付を入れる |
| 「次は〇〇をやってほしい」「〇〇に着手」 | 担当を入れ、「進行中」にする。行が無ければ足す |
| 進め方の手順（①〜③など） | 大きい作業の行のメモに要約し、手順の1つずつを行として足す |
| 「後回し」「優先度下げる」「廃止の確率大」 | 「保留」にし、優先度を下げ、理由をメモに書く |
| 画面への指摘（「〇〇は不要」「文字が見えない」） | UI の行として足すか、近い行のメモに書き足す |
| 雑談・お礼・感想だけ | 拾わない |

- 日付は、チャットの日付の区切り（「2026.11.03 火曜日」など）とタイムスタンプから決める。深夜の発言は日付をまちがえやすいので、区切りの行を必ず確かめる
- 発言から読めないこと（完了日・担当）は推測で埋めず、空けておき、報告で「確認が要る」と書く

## 直し方

- 区分ごとに3つの表（機能開発・UI・分析）。列は `タイトル | 担当 | 状態 | 優先度 | 期限 | 完了日 | 関連 | メモ`
- 状態：未着手／進行中／完了／保留（「進行中（ほぼ完了）」のような書き足しはそのまま残す）。優先度は MoSCoW：Must／Should／Could／Won't
- 完了日は `11/3` の形（年は書かない）。burndown.py はこの形で読む
- セルの中の改行は `<br>`。`|` はセルの中に書かない
- 担当は、チャットや報告に書かれたとおりに入れる。メンバーが自分で書いた中身（状態・メモ）は消さず、書き足すときは `<br>` で後ろにつなぐ
- 冒頭の注記（管理・書き方）と「バーンダウン」の節の文は、頼まれない限り書き足さない。管理者の名前や、担当の割り振りの決まりは書かない

## バーンダウンの数え方

- バックログの全行を数え、完了日がある行をその日に減らす。理想の線は 11/14 から 12/27（本応募の締切）で 0
- 完了日が空の「完了」は、描いた日に終えたものとして数える（報告で、完了日を入れてほしいと伝える）
- 行を足すと全体の件数が増え、線が上にずれる。報告では「増えた分」と「進んだ分」を分けて書く
