# 仕様書：議案を裁く裁判ゲーム（ハッカソン作品）

用語は `GLOSSARY.md`、設計判断は `docs/adr/0001`・`0002` に従う。

## Problem Statement

投票権を持つ前の中高生にとって、政治は「大人の世界の遠い話」で、自分の生活と結びついていない。地方議会では、部活動のように中高生の毎日に直結する議題が実際に話し合われているのに、そのことを知る機会もなく、賛成と反対それぞれの根拠を比べて自分で判断する経験もない。授業で教えられる「主権者教育」は教材っぽさが強く、自分から関心を持つきっかけになりにくい。

## Solution

ダンガンロンパのような「捜査して、裁判で矛盾を崩す」ゲームの型を使い、中高生が議案を裁く側に立つゲームを、スマホサイズのWebアプリとして作る。

舞台は、大事なことを生徒による裁判で決める架空の学園。議案は「部活動を廃止して、外部のクラブに任せるか」。プレイヤーは賛成側・反対側のどちらにもつかない検証役として、捜査で証拠を集め、裁判で両方の論者の根拠のない主張を崩していく。最後に賛成か反対かを自分で投票し、みんなの投票結果と比べる。そのあとで「この議案は、実際に全国の地方議会で話し合われている『部活動の地域展開』だった」と元の議題を明かし、自分の住む市の議会での調べ方を紹介して終わる。

通しで遊んで10〜15分。ハッカソンでは、主張を1つ崩す場面を山場にした3分のデモで見せる。

## User Stories

### 中高生のプレイヤー：始める

1. 中高生のプレイヤーとして、URLを開くだけでスマホのブラウザですぐ遊び始めたい。アプリのインストールやログインをしたくないから
2. 中高生のプレイヤーとして、縦画面のまま片手で操作したい。休み時間や移動中にも遊べるようにしたいから
3. 中高生のプレイヤーとして、最初に学園の「生徒による裁判」の制度を短く説明してほしい。なぜ議案を裁くのかがわかるから
4. 中高生のプレイヤーとして、今回の議案（部活動を廃止して外部のクラブに任せるか）を最初にはっきり示してほしい。何について考えるのかがわかるから
5. 中高生のプレイヤーとして、自分が検証役で、どちらの側にもつかないことを最初に知りたい。誰かを論破するゲームではなく、主張の中身を確かめるゲームだと理解できるから

### 中高生のプレイヤー：捜査

6. 中高生のプレイヤーとして、2Dの一枚絵の気になる所をタップして調べたい。直感的に証拠を探せるから
7. 中高生のプレイヤーとして、調べた所から証拠が手に入ったとき、それがはっきりわかるようにしてほしい。集め漏れに気づけるから
8. 中高生のプレイヤーとして、集めた証拠をいつでも一覧で見返したい。裁判で使う前に中身を確認できるから
9. 中高生のプレイヤーとして、証拠ごとに、それが何のデータなのか（どこの調査か、いつのものか）を見たい。データの出どころを意識できるから
10. 中高生のプレイヤーとして、論者たちから話を聞いて、それぞれの立場と言い分を事前に知りたい。裁判で誰が何を言いそうかを予想できるから
11. 中高生のプレイヤーとして、証拠が5つそろったら裁判に進めるようにしてほしい。準備が整ったことがわかるから
12. 中高生のプレイヤーとして、どの主張にも使えないひっかけの証拠も混ざっていてほしい。「それっぽいデータ」をうのみにしない練習になるから

### 中高生のプレイヤー：裁判

13. 中高生のプレイヤーとして、3Dの裁判場で、発言する論者にカメラが回り込む演出を見たい。議論の緊張感を感じられるから
14. 中高生のプレイヤーとして、6人の論者（賛成3・反対3）がそれぞれ自分の立場から主張するのを聞きたい。一つの議案に多くの利害関係者がいることがわかるから
15. 中高生のプレイヤーとして、どの論者も悪役ではなく、一理ある主張をしていると感じたい。現実の政治の議論もそうだと知れるから
16. 中高生のプレイヤーとして、流れてくる主張の中から、根拠のない主張を見つけたい。議論の穴に気づく力が試されるから
17. 中高生のプレイヤーとして、根拠のない主張に、それを崩す証拠を突きつけたい。証拠で主張を崩す気持ちよさを味わえるから
18. 中高生のプレイヤーとして、反射神経ではなく、よく考えれば解ける形にしてほしい。アクションが苦手でも最後まで遊べるから
19. 中高生のプレイヤーとして、間違った証拠を突きつけたら、その場面をやり直したい。なぜ間違えたかを考え直せるから
20. 中高生のプレイヤーとして、間違えたときに、少しだけヒントがほしい。詰まって投げ出さずに済むから
21. 中高生のプレイヤーとして、主張を崩したとき、その主張のどこがおかしかったのか（データの読み違い、一部だけを全体のように言う、など）を説明してほしい。同じパターンを現実でも見抜けるようになるから
22. 中高生のプレイヤーとして、賛成側と反対側の根拠のない主張を2つずつ崩したい。どちらの側にも弱い主張と強い主張があると体感できるから
23. 中高生のプレイヤーとして、根拠のない主張を崩したあとにも、両方の側に筋の通った主張が残っていてほしい。最後の投票で本当に迷えるから

### 中高生のプレイヤー：投票とエンディング

24. 中高生のプレイヤーとして、裁判の最後に、議案に賛成か反対かを自分で選びたい。自分の判断で結論を出す経験ができるから
25. 中高生のプレイヤーとして、どちらに投票しても「正解」「不正解」と言われないでほしい。自分の意見を否定されないから
26. 中高生のプレイヤーとして、投票の前に、残った筋の通った主張を両方の側から振り返りたい。判断の材料を整理できるから
27. 中高生のプレイヤーとして、投票したあと、みんなの投票結果を見たい。自分の判断がほかの中高生と比べてどうなのかを知りたいから
28. 中高生のプレイヤーとして、みんなの投票結果が通信できずに取得できなくても、エンディングを最後まで見たい。通信の不調で体験が途切れないから
29. 中高生のプレイヤーとして、この議案が実際に全国の地方議会で話し合われている「部活動の地域展開」だったと明かしてほしい。ゲームの話が現実とつながっていると気づけるから
30. 中高生のプレイヤーとして、元の議題について、国のガイドラインや実際の議会資料へのリンクがほしい。もっと知りたくなったときに調べられるから
31. 中高生のプレイヤーとして、自分の住む市の議会で同じ議題が話されているか、議事録の調べ方や傍聴の方法を知りたい。ゲームの外で政治に関わる最初の一歩になるから
32. 中高生のプレイヤーとして、もう一度最初から遊び直したい。別の投票をしたらどう感じるか試せるから

### 中高生のプレイヤー：安心して遊ぶ

33. 中高生のプレイヤーとして、名前やメールアドレスなどを入力せずに遊びたい。個人情報を出さずに済むから
34. 中高生のプレイヤーとして、ゲームの内容が特定の政党や意見を推していないと感じたい。押しつけられている気がせず、素直に考えられるから

### 発表者（チーム）

35. 発表者として、3分のデモで「議案の提示 → 捜査を1か所 → 主張を1つ崩す山場 → 投票 → みんなの投票結果 → 元の議題の種明かし」を通したい。限られた時間で作品の価値を伝えられるから
36. 発表者として、デモを毎回同じ流れで、事故なく再現したい。本番で失敗しないから
37. 発表者として、デモ用に、捜査や裁判の途中から始められるようにしたい。3分に収めるため、見せたい場面へすぐに飛べるから
38. 発表者として、スマホサイズの画面を、PCのブラウザやスクリーン投影でも崩れずに表示したい。会場のスクリーンに映せるから
39. 発表者として、みんなの投票結果に、デモの時点である程度の票数が入っていてほしい。結果の見せ場が成立するから

### シナリオ担当

40. シナリオ担当として、論者・主張・証拠・正しい組み合わせ・説明文を、コードを書かずにデータとして編集したい。開発者を待たずにシナリオを直せるから
41. シナリオ担当として、編集したシナリオデータに矛盾（存在しない証拠を参照している、崩せない主張がある、など）があれば、すぐに知らせてほしい。壊れたシナリオでデモを迎えないから
42. シナリオ担当として、編集したシナリオを、すぐに通しで遊んで確かめたい。テンポや難しさを体感で調整できるから
43. シナリオ担当として、どの証拠や主張が、元の議題のどの資料にもとづいているかを記録したい。本物のデータを使っていることを説明できるから
44. シナリオ担当として、賛成側と反対側の根拠のない主張・筋の通った主張の数が釣り合っているかを確かめたい。中立性を保てるから

### アート担当

45. アート担当として、7人分（検証役と論者6人）の立ち絵を、表情の差分つきで差し替えられるようにしたい。描いた絵をすぐにゲームで確認できるから
46. アート担当として、捜査用の一枚絵で、調べられる場所の位置を絵に合わせて調整したい。絵とタップできる範囲がずれないから

### 開発者

47. フロントエンド開発者として、ゲームの進行ロジックを3Dの表示から切り離したい。演出を作り込んでも遊びの流れが壊れないから
48. バックエンド開発者として、匿名の投票を受け付けて集計するAPIを、フロントエンドと決めた約束どおりに提供したい。並行して開発できるから
49. バックエンド開発者として、同じ人が何度も投票して結果をゆがめることを、個人情報を集めない範囲で緩やかに防ぎたい。みんなの投票結果がある程度信頼できるから

## Implementation Decisions

### 全体の構成

- スマホサイズ・縦画面のWebアプリ。ログインなし。TypeScript で作る
- フロントエンドは React と React Three Fiber。3Dは裁判場だけで、捜査は2Dの一枚絵、論者は2Dの立ち絵（1か月・フロントエンド1人という条件からの判断）
- AIによる反論は使わず、裁判の流れはすべてシナリオデータで決める（ADR 0001）

### モジュール

1. **ゲーム進行モジュール**（一番大事な、深いモジュール）
   - 捜査・裁判・投票・エンディングの進み方をすべて持つ。描画や通信には依存しない
   - 外から見えるのは、ほぼ次の3つだけ：
     - シナリオデータから初期状態をつくる
     - 現在の状態にプレイヤーの操作を適用して、次の状態を返す
     - 現在の状態から、画面に出すべきもの（今の場面、発言中の論者、選べる操作）を取り出す
   - プレイヤーの操作は「調べる場所をタップする」「論者の話を聞く」「主張に証拠を突きつける」「先へ進む」「投票する」「やり直す」の数種類
   - 状態は大きく「導入 → 捜査 → 裁判 → 投票 → エンディング」と進む。裁判の中では、根拠のない主張4つを順に崩していく
   - 間違った証拠を突きつけたら、その主張の場面の頭に戻る（ヒントの段階を1つ進める）
   - 投票には正解を持たない。賛成・反対のどちらでもエンディングに進む
   - デモ用に、任意の場面から始められる初期状態をつくれる

2. **シナリオデータと検証**
   - シナリオは、議案・論者6人・証拠5つ・主張（根拠のない主張4つと筋の通った主張）・正しい組み合わせ・崩したときの説明・ヒント・元の議題の資料リンクを持つデータ
   - 読み込むときに検証して、次のような矛盾を知らせる：存在しない証拠や論者を参照している、崩せない根拠のない主張がある、賛成側と反対側の根拠のない主張の数が釣り合っていない
   - 本物のデータを使った証拠には、出典（資料名・発行元・時期）を必ず持たせる
   - バックエンドが用意する管理の仕組みで、シナリオ担当がこのデータを編集する。編集結果はフロントエンドが読み込む静的なデータとして書き出す（ゲーム中にシナリオを通信で取りに行かない）

3. **3D裁判場**
   - ゲーム進行モジュールが返す「発言中の論者」を受け取って、カメラの回り込みと立ち絵の表示を行うだけの層。ゲームのルールは持たない

4. **捜査画面・UI**
   - 一枚絵と調べられる場所の配置、証拠の一覧、論者の話を聞く画面、投票画面、エンディング画面

5. **投票集計API**
   - 匿名の投票（賛成・反対）を受け付けて、みんなの投票結果（賛成数・反対数）を返す、2つの操作だけの小さなAPI
   - 個人を特定できる情報は受け取らず、保存もしない
   - 同じ端末からの重複投票は、端末に残す匿名の目印で緩やかに防ぐ（厳密さよりも、個人情報を持たないことを優先する）
   - 通信に失敗しても、ゲームはエンディングまで進める（みんなの投票結果を出す場面だけ「取得できませんでした」と表示する）

### シナリオの中身（決定済み）

- 舞台：大事なことを生徒による裁判で決める、架空の学園
- 議案：部活動を廃止して、外部のクラブに任せるか
- 元の議題：部活動の地域展開。国は令和8〜13年度を「改革実行期間」として、休日については原則すべての部活動の地域展開を目指している
- 論者：
  - 賛成側（外部のクラブに任せる）：先生の負担を訴える生徒、専門的な指導を受けたい生徒、生徒会の財政担当
  - 反対側（部活を残す）：家庭の費用負担を心配する生徒、地域にクラブがない地区から通う生徒、部活が居場所になっている生徒
- 根拠のない主張は賛成側2・反対側2。証拠は5つで、そのうち1つはひっかけ
- エンディング：みんなの投票結果 → 元の議題の種明かしと資料リンク → 自分の市の議会の調べ方（議事録の検索、傍聴）

## Testing Decisions

- よいテストとは、外から見える振る舞いだけを確かめるテスト。モジュールの中の状態の持ち方や関数の分け方には触れず、「この操作をしたら、こうなる」だけを書く
- テストする境目は2か所だけにする
  1. **ゲーム進行モジュール**：シナリオデータとプレイヤーの操作の並びを入れ、得られる状態を確かめる。例：
     - 正しい証拠を突きつけると主張が崩れ、次の主張に進む
     - 間違った証拠を突きつけると、その主張の場面の頭に戻り、ヒントが1段進む
     - 根拠のない主張4つをすべて崩すと投票に進む
     - 賛成・反対のどちらに投票してもエンディングに進む
     - デモ用の途中の場面から始めても、最後まで進める
     - 本番のシナリオデータで、最初から最後まで通しで遊べる（シナリオ担当がデータを直したときの回帰テストになる）
  2. **シナリオデータの検証**：ゲーム進行モジュールの入口として、矛盾したシナリオを読み込ませると、どの矛盾かがわかる形で知らされることを確かめる
  3. **投票集計API**：投票を送るとみんなの投票結果に反映されること、個人を特定できる情報を受け取らないこと、壊れた入力を拒否することを、HTTPの約束ごととして確かめる
- 3Dの裁判場の演出と画面の見た目は自動テストしない。デモの3分の道筋を、本番と同じ端末と投影環境で手で通して確認する
- 既存のコードはないため、参考にできる過去のテストはない

## Out of Scope

- 2章目以降や、ほかの議題（ボリュームは1章分のみ）
- ハッカソン後の運営、議題の追加、保守
- 複数人が同時に遊ぶモード（クラス全員で議論する、など）
- AIによる反論や、自由に書いた主張への応答（ADR 0001）
- 3Dで動き回る捜査、3Dの論者モデル
- 反射神経を試すミニゲーム
- ログイン、アカウント、個人を特定できる情報の収集
- 現実の政党名・議員名を出すこと（ADR 0002）
- スマホアプリ（App Store／Google Play）としての配布
- 殺人や処刑の描写

## Further Notes

- 期間は1か月。チームは5人（フロントエンド1・バックエンド2・シナリオ1・アート1）
- 審査はデモを見るだけ。審査員が自分で遊ぶことは想定しない。最優先は「デモで見せる道筋が毎回確実に動くこと」
- フロントエンド1人に作業が集中しやすい。ゲーム進行モジュールを先に固め、3D演出はそのあとで作り込む。捜査と裁判の面白さは、仮の絵とテキストで早めに確かめる
- バックエンドの2人は、投票集計APIとシナリオの管理の仕組みに加え、シナリオデータの検証を担当すると、フロントエンドの負担を減らせる
- 証拠に使う本物のデータは、出典を必ず記録する。発表の質疑で「本当のデータか」と聞かれたときの根拠になる
- 中立性（ADR 0002、検証役が両方の側を崩すこと）は、発表で強調すべき設計上の工夫
