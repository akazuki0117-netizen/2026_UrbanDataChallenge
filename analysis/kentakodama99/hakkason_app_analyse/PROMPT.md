# プロンプト：東京都オープンデータハッカソン「勝てるアプリ／勝てないアプリ」分析

> 使い方：以下の「---」から下を、そのまま Claude Code（ブラウザ操作・Web 取得・ファイル書き込みが使える環境）に渡す。
> 作業フォルダ（`WORKDIR`）はこのファイルと同じ `analysis/kentakodama99/hakkason_app_analyse/`。

---

## 0. あなたの役割とゴール

あなたはハッカソン審査傾向を分析するリサーチャーである。
東京都オープンデータハッカソン 2026 年度の提出作品集
`https://odhackathon.metro.tokyo.lg.jp/collection/?year=2026`
に掲載された **全提出作品** の詳細情報を漏れなく収集し、
**ファイナリスト作品（＝勝てるアプリ）** と **非ファイナリスト作品（＝勝てないアプリ）** を比較して、
「何が勝敗を分けたのか」「なぜそうなるのか」を根拠付きで説明する Markdown レポートを作成せよ。

最終的な目的は、**我々が次に作るアプリの企画・設計・プレゼンに直接使える示唆**を得ることである。
傾向の羅列で終わらせず、「だから次はこうする」まで落とし込むこと。

## 1. 事前に分かっているサイト構造（着手時に必ず再確認すること）

| 項目 | 内容 |
|---|---|
| 一覧 URL | `/collection/?year=2026`、ページ送りは `&page=N`（1 ページ 20 件、約 25 ページ ≒ 約 500 件の見込み） |
| 掲載順 | **「掲載順はランダムです」と明記されている**。ページを跨ぐと重複・取りこぼしが起きうる |
| ファイナリスト絞り込み | ページ上のチェックボックス。`&finalist=1` は効かなかった（JS 制御の可能性大） |
| カード上の情報 | 画像、受賞バッジ（都知事杯／技術賞／学生賞 など）、**「ファイナリスト」バッジ**、タイトル、チーム名、年度 |
| 詳細 URL | `/collection/{数字ID}/?year=2026`（ID は 16〜19 桁） |
| 詳細ページの項目 | タイトル、受賞バッジ、ファイナリストバッジ、チーム名、メンバー名、サービス画像、「サービス内容」、「利用した東京都オープンデータカタログサイトの URL」、「提出作品 URL（デモ）」、「First Stage プレゼンテーション動画（YouTube）」 |

上記は事前調査の結果であり、**作業開始時に実際のページで確かめ、違えば `ANALYSIS_LOG` に記録して手順を修正すること。**

### 使うツールの使い分け

| 作業 | ツール | 理由 |
|---|---|---|
| 一覧ページ・詳細ページの取得 | WebFetch（または curl ＋ HTML 解析） | サーバー側で HTML が生成されており、JS なしでカード・本文が取れる |
| ファイナリストのチェックボックス絞り込み | **Playwright MCP** | JS で動いている可能性が高く、URL パラメータでは再現できない |
| モック（デモ URL）の確認・スクリーンショット | **Playwright MCP** | 多くが JS アプリ。画面を実際に開いて確認する必要がある |
| WebFetch で取れない・中身が欠ける場合 | **Playwright MCP** に切り替え | 切り替えた事実と理由をログに残す |

Playwright MCP では `browser_navigate` → `browser_snapshot`（アクセシビリティツリーで要素を確認）→ `browser_click` でチェックボックスを操作し、絞り込み後の一覧を `browser_snapshot` または `browser_evaluate`（`document.querySelectorAll('a[href*="/collection/"]')` 等で ID を抜く）で取得する。スクリーンショットは `browser_take_screenshot` で `data/mock/{id}.png` に保存する。

## 2. 守るべき原則

1. **全件取得を最優先**。推測で埋めない。取れなかった項目は `null` とし、理由を記録する。
2. **情報の消失を防ぐ**。取得した内容は都度ファイルに書き出し、会話のコンテキストだけに保持しない（下記 §4）。
3. **中断・再開できるようにする**。どこまで終わったかを常にファイルで分かる状態にし、再開時は既取得 ID をスキップする。
4. **サイトに負荷をかけない**。リクエスト間隔は 1〜2 秒以上空ける。並列アクセスはしない。`robots.txt` を確認する。
5. **個人情報は分析に使わない**。メンバー氏名は保存しない（人数のみ数える）。チーム名は作品の識別用に保存してよい。
6. **事実と解釈を分ける**。レポートでは「データからの事実」「考えられる理由（仮説）」「我々への示唆」を書き分ける。

## 3. 手順

### Phase 1：一覧の全件収集（ID リストの確定）

1. 一覧 1 ページ目を開き、総件数・総ページ数を確認する（表示があれば記録）。
2. `page=1` から最終ページまで順に取得し、各カードから `id / title / team / badges（受賞・ファイナリスト）/ 詳細URL` を抜き出して `data/list_raw.jsonl` に 1 行 1 件で追記する。
3. **ランダム順対策**：ID で重複除去する。全ページ一巡後、ユニーク件数が想定総件数に届かない場合は、新規 ID が出なくなるまで（目安：連続 2 巡で新規 0 件）再巡回する。巡回ごとの新規件数をログに残す。
4. **ファイナリスト集合の確定（2 系統で照合）**：
   - (a) カード／詳細ページの「ファイナリスト」バッジで判定
   - (b) ブラウザ操作でファイナリストのチェックボックスを ON にし、表示される一覧（ページングがあれば全ページ）の ID を取得
   - (a) と (b) が一致することを確認し、不一致があれば両方を記録して詳細ページで個別確認する。
5. `data/works_index.csv`（id, title, team, is_finalist, awards, detail_url）を出力し、件数（全体／ファイナリスト／受賞別）をログに記録する。

### Phase 2：詳細ページの収集

全作品の詳細ページを 1 件ずつ開き、以下を `data/details/{id}.json` として **1 作品 1 ファイル** で保存する（取得済みならスキップ）。

```json
{
  "id": "", "url": "", "fetched_at": "ISO8601",
  "title": "", "team": "", "member_count": 0,
  "is_finalist": true, "awards": ["都知事杯"],
  "service_description": "（サービス内容の全文。要約しない）",
  "open_data_urls": ["..."],
  "external_data_urls": ["東京都カタログ以外のデータ URL"],
  "demo_url": "", "video_url": "", "image_count": 0,
  "notes": "取得できなかった項目や異常"
}
```

- 「サービス内容」は **要約せず原文のまま** 保存する（後で分析し直せるように）。
- 失敗した ID は `data/failed.txt` に記録し、最後にまとめて再試行する。

### Phase 3：モック（提出作品 URL）の確認 ― 選択的に実施

全件は不要。以下を対象とする：
- **ファイナリスト全件**
- **比較対照として非ファイナリストから無作為に同数程度**（乱数シードを記録）

各デモ URL を開き、`data/mock/{id}.json` に以下を記録する（スクリーンショットが撮れる環境なら `data/mock/{id}.png` も保存）。
- 動作状況（動く／リンク切れ／ログイン必須／動画のみ 等）
- 提供形態（Web アプリ、スマホアプリ、LINE ボット、地図、3D、ダッシュボード、紙・企画書 等）
- 最初の画面で「何のアプリか」が 5 秒で分かるか（はい／いいえ＋一言）
- 主要機能の数、生成 AI の利用有無、地図・可視化の有無
- 完成度の印象（プロトタイプ／実用レベル）と根拠

プレゼン動画（YouTube）は、ファイナリストについて **説明欄・タイトル・長さ** が取れれば記録する（視聴による文字起こしは必須ではない）。

### Phase 4：特徴量化（コーディング）

**先にコードブック（分類基準）を作り `codebook.md` に保存してから**、全作品に同じ基準で付与する。後から基準を変えたら全件やり直す。

| 観点 | 例 |
|---|---|
| テーマ領域 | 防災、福祉・介護、子育て、教育、観光、交通・移動、環境、健康・医療、行政手続き、まちづくり、地域コミュニティ、その他 |
| 想定ユーザー | 都民一般／特定の困りごとを持つ人（高齢者・障害者・外国人・子育て世帯 等）／行政職員／事業者 |
| 課題の具体性 | 「誰の・どんな場面の・どんな困りごと」が明示されているか（3 段階） |
| 解決の形 | 情報提供・検索／可視化・地図／マッチング／意思決定支援／ゲーム化・体験／行動変容 |
| 使用データ | 東京都カタログのデータ数、データ種類、他データ（国・民間・OSM 等）との掛け合わせ有無 |
| データの使い方 | 表示するだけ／加工・集計／複数データを結合して新しい指標を作る |
| 技術 | 生成 AI・LLM、地図、3D・AR、機械学習、ネイティブアプリ 等 |
| 提出物 | デモ URL の有無と動作、動画の有無、画像枚数 |
| 説明文 | 文字数、構成（課題→解決→データ→効果 の順か）、数字・根拠の有無、行政施策との接続への言及 |
| 実装・継続性 | 運用主体、行政が採用できるか、費用・持続性への言及 |
| チーム | 人数、学生チームか（判別できる範囲で） |

- 判定が微妙なものは `uncertain` とし、理由を残す。
- 精度確認として、ファイナリストから 10 件程度を **2 回独立にコーディング** し、一致率をレポートに記載する。

### Phase 5：分析

1. **基本集計**：全体件数、ファイナリスト率、受賞の内訳。
2. **観点別の比較**：各特徴について「ファイナリスト群での割合」と「非ファイナリスト群での割合」、その比（リフト）を表にする。件数が少ないので、件数そのものも必ず併記し、**少数サンプルである旨を明記**する（必要なら Fisher の正確検定などで参考値を出す）。
3. **組み合わせの傾向**：単一要因だけでなく、「テーマ × 解決の形」「データ数 × 結合の有無」など勝ち筋になりやすい組み合わせを探す。
4. **テキスト比較**：ファイナリストと非ファイナリストの「サービス内容」で頻出する語・言い回し・構成の違い。
5. **ファイナリスト事例の読み込み**：全ファイナリストについて「なぜ選ばれたと考えられるか」を 2〜3 行で書く。受賞作（都知事杯・技術賞・学生賞 等）は個別に深掘りする。
6. **負けパターンの抽出**：非ファイナリストに多い特徴（例：課題が抽象的、データを表示するだけ、デモが動かない 等）を、具体例 ID 付きで示す。
7. **審査基準との照合**：大会公式サイトの審査基準・評価観点・テーマを確認し、見つかった傾向が審査基準のどこに対応するかを対応表にする。出典 URL を記載。
8. **（任意・時間があれば）過去年度との比較**：`/collection/2025/` 〜 `/collection/2021/` のファイナリストについても同じ手順を簡易に行い、年をまたいで変わらない傾向／その年だけの傾向を分ける。

### Phase 6：レポート作成

`reports/勝てるアプリ分析_2026.md` を作成する。構成：

1. **結論（先頭 1 画面で読める長さ）**：勝てるアプリの条件 TOP5、勝てないアプリの典型 TOP5
2. 調査概要：対象・取得日・件数・方法・限界
3. 基本集計
4. 観点別の比較表（件数・割合・リフト）
5. 勝ちパターン（組み合わせ）と代表事例（作品名・リンク）
6. 負けパターンと代表事例
7. 受賞作の深掘り
8. 審査基準との対応表
9. **なぜそうなるのか（仮説）**：審査員・主催者（東京都）の立場から見た理由。事実と仮説を明確に分ける
10. **次のアプリ作成への示唆**：企画・データ選び・実装・デモ・プレゼンの各段階での「やること／避けること」チェックリスト
11. 我々のアイデア（リポジトリの `idea/` 配下、`docs/contest.md`）をこのチェックリストで採点した結果（あれば）
12. 分析の限界：ファイナリストが少数であること、相関であって因果ではないこと、審査にはプレゼン本番など公開情報に表れない要素があること、ランダム掲載・取得漏れの可能性
13. 付録：全作品一覧（ID・タイトル・ファイナリスト有無・主要特徴）、コードブックへのリンク

各主張には、根拠となる **件数** または **作品 ID／リンク** を必ず付けること。

## 4. ログと保存のルール（情報の消失防止）

作業フォルダ構成：

```
analysis/kentakodama99/hakkason_app_analyse/
├─ PROMPT.md                 … このプロンプト
├─ progress.md               … 進捗チェックポイント（常に最新に上書き）
├─ codebook.md               … 分類基準
├─ data/
│  ├─ list_raw.jsonl         … 一覧の生データ（追記のみ）
│  ├─ works_index.csv        … 確定した作品一覧
│  ├─ details/{id}.json      … 詳細ページ（1 作品 1 ファイル）
│  ├─ mock/{id}.json|png     … モック確認結果
│  ├─ features.csv           … コーディング結果
│  └─ failed.txt             … 失敗した ID
└─ reports/勝てるアプリ分析_2026.md
```

- **`progress.md`**：「現在の Phase／完了件数／総件数／次にやること／未解決の問題」を、**10 件取得ごと、および各 Phase 終了時** に上書き更新する。中断後はまずこれを読んで再開する。
- **`analysis/kentakodama99/ANALYSIS_LOG.md`**：各 Phase の終了時、および方針を変えた時に 1 行追記する（日付・やったこと・判断・出典）。新しいものを上に足す。
- 生データ（`list_raw.jsonl`, `details/`）は上書き・改変しない。加工結果は別ファイルに出す。
- 取得日と出典 URL を必ず残す。

## 5. 完了条件（すべて満たすまで終わらない）

- [ ] 一覧のユニーク件数が、サイト表示の総件数（またはページ数×20 から推定した件数）と一致、または差分の理由が説明されている
- [ ] ファイナリスト集合が 2 系統（バッジ／チェックボックス絞り込み）で照合済み
- [ ] 全作品の `details/{id}.json` が存在し、`failed.txt` が空、または残りの理由が記載されている
- [ ] ファイナリスト全件と対照群のモック確認が済んでいる
- [ ] コードブックが保存され、二重コーディングの一致率が出ている
- [ ] レポートの各主張に件数または作品 ID の根拠がある
- [ ] `progress.md` と `ANALYSIS_LOG.md` が最新

途中で判断に迷う点（例：ファイナリストの定義が曖昧、総件数が合わない、サイトがアクセスを拒否する）があれば、**勝手に仮定して進めず**、状況と選択肢をまとめて確認を求めること。
