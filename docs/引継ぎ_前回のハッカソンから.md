# 引継ぎ：前回のハッカソンから UDC2026 へ

前回のハッカソン（同じメンバーで参加、2026/11/20 提出）の振り返り会で出た話を、UDC2026（Politica）に持っていく形にまとめた。

- 対象：UDC2026 のメンバー全員
- いつ読む：11/21 の会議の前。会議の最初に「やるべきこと」の3つを読み上げる
- 期間の違い：前回は約5週間。UDC は **11/21〜12/27 の約5週間**で、ほぼ同じ長さ。最初の1週間の使い方が勝負になる

## 1. 続けること（よかったこと）

| よかったこと | UDC でどう続けるか |
|---|---|
| コンテストが始まる前から、リポジトリ・テーマ選び・分析を進めていた | すでにリポジトリと事前キックオフ（11/14）は済んでいる。分析（オープンデータ）も先に手を付ける |
| 議事録・アジェンダ・バックログの型（skills）がそろっていた | 同じ型を使う。バックログは `app/planning/プロダクトバックログ.md` だけで管理する |
| 自治体への**ヒアリング**で「困っていること」を直接聞いてから考えたら、発想が早かった | 教育・政治の現場（学校・選挙管理委員会など）に話を聞ける場を探す |
| **コンセプトがシンプル**で、コアが1つだった。説明しやすく作りやすかった | Politica も「何をするアプリか」を1文で言えるところまで絞る |
| **入力を最小限**に削った。「機能は必要最低限」 | 画面・入力項目は最初から少なく。足すより削る |

| 定例を週1〜2回にした | 同じ頻度で。平日に出られない人は土日に合わせる |
| k-masahiro116のレビュー（アクセシビリティ・デザイン思考の観点）が効いた | レビューの関門をk-masahiro116にする |
| Figma はコメントが入れやすく、過去の版が残る | 画面・資料のレビューは Figma。ページは左から右に一列に並べる |

## 2. やるべきこと（変えること）

### いちばん大事な3つ

1. **アイデアを出す前に、目的・ターゲット・出したい効果を決める**
   - 前回は、無から量を出して軸がぶれた。ヒアリングのあとに出した案は早かった
   - Politica は「選挙権のない未成年」「政治への参画」までは決まっている。**どんな場面で、何が変わったら成功か**を先に決める
2. **要件定義に、期間の半分を使ってもいい。特に技術要件は最初に詰める**
   - ディレクトリ構成、Cloudflare の構成、バックエンドと API の受け渡し、JSON の形
   - 要件をまとめたら「この要件定義で認識の違いはないか」を全員に確認する
   - 機能要件は膨らむので、抑えながら変えていく
3. **開発は「画面ごと」ではなく「フロント」と「バックエンド」で分ける**
   - 前回は画面ごとに分けて、裏の辻褄が合わず、一人に開発が集中した
   - 開発・テスト・ログが見られる環境を最初に整える（前回はログが見られず、テストの手段もなかった）

### ほかに出たこと

- **目的は1つにしぼってぶらさない**。機能に優先順位をつけてスリムに
- 1人でも完結して、ちゃんと動くものにする。複数人が前提のプラットフォーム型は弱くなりがち（Politica は仮想投票なので、1人でも体験できる形を意識する）
- 説明しにくい機能ほど、**プロトタイプを作って見せる**
- **最初にデザインのルール（色など）を決め**、全員でそれに合わせる。UI は生成した案をコードに落とす
- **資料と動画の役割を最初に決める**。資料は前提・ロジック・効果、デモ動画は「実際に使う様子」。同じ説明を2回しない
- 資料・動画を**駆け込みにしない**。デモ動画の構成は早めに決めて、k-masahiro116のレビューを通す
- **期待効果の数字**は、根拠を残し、相手（審査員）に合わせて大きさを決める。数字の出し方はチームで先に合意しておく
- 発表の前に**質疑の対策**の時間（1時間ほど）を取る。一度発表して、みんなで突っ込む
- データや資料の置き場所を1か所にまとめる（前回は散らばって追いきれなかった）
